1 · Start a migration

A run imports data for ONE church. Everything it stages or loads belongs only to that church, and every load can be undone.

New migration

Which product is the church moving from? Known column names from that product map automatically. Preset (unverified) means no real export from that product has been run end to end yet — review every mapping.

2 · Upload the exported files

Drop every file from the old system at once — CSV, Excel (.xlsx / .xls) or JSON. Each file is captured as-is, profiled, and given a data type from its column names; change the type if it guessed wrong. The same file for the same church is refused unless you choose to import it again. Nothing live is touched.
Drop files here
or click to choose (several at once is fine)

3 · Map columns and values

One tab per file. Required columns come first (*). AUTO = high confidence; REVIEW = please check. Confirm or change any row; values such as funds, roles and payment methods are unified below before anything is staged.

4 · Review: validate and decide

Each data type is staged and validated on its own. Pick a tile to see its rows. Possible duplicates must be decided (Skip / Update / Merge / Import as new) before the type can be approved. Still nothing live.
Working on: family
Download validation report (CSV)

5 · Load to live data

Types load in this order — people and the records others refer to first — and a type waits for the ones it depends on. Loading writes the approved rows into this church's live data, tenant-stamped, honouring every decision. Every batch can be rolled back; Roll back run undoes all of them in reverse order.
